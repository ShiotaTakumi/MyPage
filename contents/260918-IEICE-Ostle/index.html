Computer Experiments on Boards of Finite Size

This page accompanies Sect. 5 of “Computational Complexity and Computer Analysis of Generalized Ostle”. It gives the full results, the machine details and the source code, which are omitted from the paper for space. The sources can be read in the source browser, or downloaded as a zip archive.

1. What was computed

The hole-free initial position was solved on every $m \times n$ board with $2 \le m \le 5$ and $1 \le n \le 5$, for capture thresholds one and two, by retrograde analysis: 20 boards, both thresholds. Capture threshold two is vacuous when $n = 1$, since a player with a single marker can never lose two.

Terminology
  • A state is a configuration, the player to move, and the move forbidden by the repetition rule. It is the unit of computation.
  • A position is a configuration, the player to move, and the configuration before the opponent’s last move, as defined in Sect. 2. The positions counted below are those reachable from the initial position.
  • B: Black (the first player) wins; W: White (the second player) wins; D: draw.

2. Environment

  • Apple Mac Studio (Mac15,14), Apple M3 Ultra, 28 cores
  • 256 GiB of memory (274,877,906,944 bytes)
  • macOS 15.3 (build 24D2059)
  • Homebrew GCC 15.2.0, -O2 -std=c++17, no external libraries

3. Method

States are addressed by a combinatorial ranking of the marker placements. No hash table is needed, and the whole state space is held in memory.

Under capture threshold $q$, a player who has lost $q$ markers loses, so every non-terminal position has at least $p - q + 1$ markers per player, where $p$ is the initial number. The states therefore split into $q^2$ blocks, indexed by the pair (markers of the player to move, markers of the opponent). A capture never increases the total number of markers on the board, so the blocks can be solved in increasing order of that total, and the working set is a single block. This is what makes capture threshold two tractable in the time and memory reported below.

Soundness of the parallel sweep

The retrograde analysis runs on 28 threads. A value changes only from unknown to win or loss, never back, so a thread that reads a stale value reads unknown and merely defers the update to the next sweep. The sweep that makes no change performs no write, so every read in it is current and the fixed point is sound.

5. Verification

No previously published solver handles capture threshold two, so the code was checked as follows.

CheckResult
The ranking is a bijection (round trip, including $5 \times 5$ with threshold two)no mismatch
With threshold one, the ranking agrees index by index with the earlier one-capture solveridentical
With threshold one, the solver reproduces that solver’s win / loss / draw countsidentical on every board
With threshold two, two independent implementations agree position by positionno mismatch over 326,053,916 positions
Parallel and single-threaded runsidentical counts

One of the two implementations indexes the whole state space; the other keeps only reachable states in a hash table. They share no code.

On the repetition rule

Sect. 2 forbids every move that reproduces the configuration before the opponent’s last move, whereas a state here stores only the single reverse of the last move. These agree because a move that pushes a marker off the board reduces the marker count and hence cannot be undone, so at most one move returns to the previous configuration.

This was verified exhaustively over the whole state space, not merely the reachable part, for six boards with capture threshold two (qdupcheck.cpp). The number of move pairs reaching the same configuration with no marker removed was zero in every case.

6. Source code and reproduction

The sources can be read in the source browser, or downloaded as a zip archive. C++17, no external libraries.

The archive and the source browser contain the following files. 

src/
├── rankgenq.h          ranks placements with unequal marker counts; splits the states into blocks
├── solveq.cpp          the solver: indexed retrograde analysis, block by block, on 28 threads
├── solveqref.cpp       a second solver sharing no code: hash table, reachable states only
├── xcheckq.cpp         compares the two solvers position by position
├── countpos.cpp        counts reachable positions without solving, at constant memory
├── qdupcheck.cpp       checks the repetition rule as described above
├── rankgenqtest.cpp    round-trip test of the ranking, and agreement with rankgen.h at threshold one
│
│   The two below are the earlier capture-threshold-one solver, against
│   which the threshold-one results are verified.
│
├── rankgen.h           the original ranking, for equal marker counts
└── solveidx.cpp        the earlier indexed solver

results/
├── grid_q1q2.tsv       one row per board and capture threshold; the numbers in Sect. 4 above
└── peak_rss.tsv        peak resident set size per board and per program
# build
$ g++ -O2 -std=c++17 -o solveq   src/solveq.cpp
$ g++ -O2 -std=c++17 -o countpos src/countpos.cpp

# outcome and counts
#   arguments: height, width, markers per player, capture threshold
$ SAVE_VALUES=v.bin ./solveq 5 5 5 2

# number of positions; reads the saved values, does not solve again
$ LOAD_VALUES=v.bin ./countpos 5 5 2

Solving $5 \times 5$ with capture threshold two needs about 27 GiB; counting its positions needs about 110 GiB. solveq takes the thread count from the environment variable THREADS; this does not change the peak memory.
